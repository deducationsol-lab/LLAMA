# Shared households and notifications

## What this change adds

Open **Shared household** in LLAMA. Each person creates a separate email/password account, confirms their email if required, and signs in. One person creates a household and generates a private, one-use invite code (expires after 24 hours). Their spouse signs in on their own device and joins using that code. A person can belong to one household; household membership controls access in Postgres RLS and security-definer RPCs with explicit membership checks. Use a recognizable household member name for attribution.

Shared bills, manually confirmed travel bookings, and school pickups live **only in the Shared household tab**. The existing dashboard's seeded records remain a separate local sample and are not silently uploaded or shared. Saving a shared record creates activity and durable notification jobs in the same transaction. Edit the electricity record to `paid`, or the travel record to `booked`, to tell the household it was manually marked that way. LLAMA doesn't actually pay or book anything.

Other signed-in household members see changes within about 10 seconds while the shared tab is open (polling plus refresh-on-focus). The activity shows the actor, record and manually selected status/time. Simultaneous edits use a revision check: stale updates fail instead of overwriting another member's change. This is not a general-purpose collaborative realtime editor.

Every opted-in device for **all current household members, including the actor**, is eligible for push. Push text is intentionally generic on the lock screen; open the notification to see the authenticated household feed. Never include children's location, financial detail or travel itineraries in push payloads.

## Required setup before live use

1. Create a dedicated Supabase project and connect its environment variables to the intended Preview environment. The server needs `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SECRET_KEY`. Only the URL/publishable key are returned by `/api/household` to the browser. Never expose the secret/service-role key through `VITE_` variables. No real household records or test accounts are seeded automatically.
2. Apply `supabase/migrations/202611020001_households.sql` **once**, as database owner, to the new database. It runs as one transaction. Use Supabase's SQL Editor or your normal migration tool. Don't run it against a database belonging to another app. All exposed tables have RLS, anonymous grants revoked, and authenticated mutation paths restricted to the checked RPCs. Push subscriptions, invites, jobs and deliveries cannot be queried directly by client roles.
3. In Supabase Authentication **URL Configuration**, set the Site URL to the intended preview URL during testing. Add that exact preview origin to allowed redirect URLs. Keep **Confirm Email** enabled and configure email delivery for your intended testers. [Redirect URL documentation](https://supabase.com/docs/guides/auth/redirect-urls), [Auth configuration](https://supabase.com/docs/guides/auth/general-configuration). The app uses email/password, not shared API access codes, for household identities. Configure password recovery through Supabase before public rollout; this initial UI does not implement an in-app recovery screen.
4. Set `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_SUBJECT` (an HTTPS contact URL or `mailto:` contact), and `CRON_SECRET`. Generate VAPID keys with the installed `web-push` library in a trusted local environment; never print private keys into shared logs or commit values. Keep the private key and cron secret server-only. A matching keypair must remain stable for existing subscriptions; rotation requires re-subscription. Preview branch keys and Production keys should be configured separately. Public key is returned to the app by `/api/household`.
5. Redeploy after environment changes. The worker is configured in `vercel.json` to run once a minute in **Production**. Preview deployments do not execute Vercel Cron Jobs. To test Preview delivery, invoke `GET /api/household?action=dispatch` from a trusted environment with `Authorization: Bearer <CRON_SECRET>`; never place that secret in a query string or expose it in frontend code. `server/index.js` routes the same endpoint locally. The cron endpoint checks the secret and never returns subscription endpoints or household details.
6. On each phone, sign in, join the same household, then explicitly select **Enable notifications on this device** and grant the browser permission. On iPhone/iPad, add LLAMA to the Home Screen first and use iOS/iPadOS 16.4+. Use HTTPS. No one can enable push remotely on another person's phone. [Apple requirements](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers.md).
7. Test two real accounts and two real devices before Production rollout. Only after that should you connect the database to Production, configure its separate push/cron secrets and merge/deploy. Existing household records are not present in Production until its database is connected.

## Reminders and delivery semantics

- Enter an event time and optional reminder time using your device's local timezone. Stored timestamps use UTC; each member sees their own local display time. A reminder must be in the next year.
- Pending bills, planned bookings and scheduled pickups can have reminders. Paid bills/done pickups do not generate reminders. Editing a record invalidates older queued reminders through its revision; set a new reminder on an edit if you still need one.
- The minute worker claims up to 20 jobs with a five-minute lease, targets only current household member subscriptions, and records per-device accepted deliveries. Transient failures retry on lease expiry, up to eight attempts. 404/410 subscriptions are removed. Successful recipients are not retried deliberately. A crash after push acceptance but before delivery bookkeeping can still cause a duplicate (the notification tag helps coalesce it). There is no exactly-once or guaranteed device-delivery promise.
- Devices offline beyond the one-hour push TTL may miss a push; activity remains in the database. Browser permission, provider availability, power/network restrictions and cron scheduling affect delivery. Do not use this as the only school pickup, payment or travel reminder system.
- Leaving a household removes membership and that user's subscriptions. Signing out disables this browser's subscription before clearing the auth session; if disabling fails, the UI reports failure rather than implying the subscription was removed. Expired/revoked permissions can require browser settings changes and re-subscription.
- This initial implementation has no member removal/admin dashboard, per-event notification preferences, account deletion UI, record deletion UI, or production-wide abuse controls. Limit invitations and use only trusted household members; keep auth rate limits and email protections configured in Supabase.

## Checks

`npm run check:household` runs Postgres-compatible SQL checks in PGlite (mock auth schema/roles, not Supabase hosted Auth) plus mocked push-worker checks. It covers two members sharing a household, outsiders/anonymous access, mutation grants, invites, stale edits, reminder validation, atomic outbox, worker leases, push-service origin validation, secret authorization, generic payloads, retry behavior and expired subscription cleanup. `npm run check:agent` still covers the independent Meta Muse endpoint. `npm run build` checks browser compilation.

These checks do **not** verify live Supabase email/auth configuration, a hosted migration, device permissions, Vercel cron execution or delivery to an actual phone. The sandbox cannot reach external database hosts; a failed migration connection must be completed from the provider's dashboard or a trusted migration environment rather than bypassing network controls.
